# CineSip Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Build a mobile-first drinking game webapp where friends split into teams, watch a movie/TV show, and drink when their team's LLM-generated rule triggers.

**Architecture:** Single Docker Compose stack on OVH VPS — React SPA (Vite + Zustand + Tailwind) served by nginx, Python/FastAPI backend with WebSocket endpoints, SQLite database (WAL mode). TMDB API for movie search, OpenRouter API (Gemini Flash) for rule generation. Real-time game state via WebSockets.

**Tech Stack:** React 18 + TypeScript, Vite, Tailwind CSS, Zustand, FastAPI (Python 3.11+), SQLite (WAL), nginx, Docker Compose, TMDB API v3, OpenRouter API (google/gemini-2.5-flash)

## Technology Decisions (Researched)

### 1. WebSockets vs Polling → **WebSockets**

**Decision: WebSockets.** FastAPI has first-class `WebSocket` support via Starlette — no extra dependencies. Use cases are textbook WebSocket territory: real-time lobby state (players joining/leaving), game events (rule triggers, drink calls), and live drink counters. Polling would waste bandwidth and add latency for a game where timing matters. Server-Sent Events could work for one-way pushes (drink notifications) but WebSockets handle the bidirectional lobby chat/join flow cleanly.

**Implementation pattern:**
- `ConnectionManager` class managing a dict of `{game_id: set[WebSocket]}` 
- JSON message protocol: `{"type": "player_joined" | "rule_triggered" | "drink_logged" | "game_started" | "game_ended", "payload": {...}}`
- Client auto-reconnect with exponential backoff (3s, 6s, 12s cap)

### 2. SQLite vs PostgreSQL → **SQLite (MVP), PostgreSQL (future)**

**Decision: SQLite with WAL mode.** Single-server deployment on OVH VPS means no horizontal scaling needed. WAL mode allows concurrent reads while a write is in progress — more than enough for a party game with 4-20 concurrent users. Zero Docker dependency (no separate Postgres container), trivial backups (copy the `.db` file), and simple migration path to PostgreSQL later via Alembic.

**SQLite config:**
```python
# Enable WAL mode, 5s busy timeout
engine = create_engine(
    "sqlite:///./data/cinesip.db",
    connect_args={
        "check_same_thread": False,  # FastAPI async
        "timeout": 5,
    },
)
# Run on connect: PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;
```

### 3. Movie Database → **TMDB API v3**

**Decision: TMDB API v3.** Industry standard, free tier, well-documented REST API. Search endpoints for movies (`/3/search/movie`) and TV shows (`/3/search/tv`) with query, year, language params. Returns poster paths, overviews, genre IDs — enough for display and context for LLM rule generation.

**Key endpoints:**
- `GET /3/search/movie?query=...&language=en-US` → movie search
- `GET /3/search/tv?query=...&language=en-US` → TV show search
- `GET /3/movie/{id}?append_to_response=credits` → movie details with cast
- `GET /3/tv/{id}?append_to_response=credits` → TV details with cast

**Auth:** Bearer token in `Authorization` header.

### 4. LLM Provider → **OpenRouter API (google/gemini-2.5-flash)**

**Decision: OpenRouter with Google Gemini 2.5 Flash.** OpenRouter provides an OpenAI-compatible endpoint (`https://openrouter.ai/api/v1/chat/completions`), so standard `openai` Python SDK works unchanged. Gemini 2.5 Flash is fast, cheap (~$0.15/M input, ~$0.60/M output), and has a 1M context window — plenty for including movie synopsis + cast + genre info as context for rule generation. Fallback models via OpenRouter's `models` array in `extra_body`.

**Integration pattern:**
```python
from openai import AsyncOpenAI

client = AsyncOpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

response = await client.chat.completions.create(
    model="google/gemini-2.5-flash",
    messages=[
        {"role": "system", "content": RULE_GENERATION_PROMPT},
        {"role": "user", "content": f"Movie: {movie_title}\nOverview: {overview}\nCast: {cast}\nGenres: {genres}"},
    ],
    response_format={"type": "json_object"},  # structured output
)
```

### 5. State Management → **Zustand**

**Decision: Zustand.** Minimal boilerplate (no Provider wrappers, no action creators, no reducers), hooks-based API, tiny bundle (~1KB), and built-in middleware for persistence and devtools. React Context would cause unnecessary re-renders across the entire tree on every state change. Redux Toolkit is overkill for ~5 stores.

**Stores needed:**
- `useLobbyStore` — room code, players, teams, connection status
- `useGameStore` — active rules, drink counts, current trigger
- `useMovieStore` — search results, selected movie, loading state
- `useUserStore` — player name, session persistence

## Data Model

### SQLite Schema

```sql
-- Core entities
CREATE TABLE games (
    id TEXT PRIMARY KEY,              -- UUID, also used as room code (first 6 chars)
    movie_tmdb_id INTEGER NOT NULL,
    movie_title TEXT NOT NULL,
    movie_type TEXT NOT NULL,         -- 'movie' | 'tv'
    movie_overview TEXT,
    movie_poster_path TEXT,
    movie_cast TEXT,                  -- JSON array of main cast names
    movie_genres TEXT,                -- JSON array of genre names
    status TEXT NOT NULL DEFAULT 'lobby',  -- 'lobby' | 'playing' | 'finished'
    team_count INTEGER NOT NULL DEFAULT 2,
    chaos_level REAL NOT NULL DEFAULT 0.5,  -- 0.0 (sipping) to 1.0 (pounding)
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    started_at TEXT,
    ended_at TEXT
);

CREATE TABLE players (
    id TEXT PRIMARY KEY,              -- UUID
    game_id TEXT NOT NULL REFERENCES games(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    team_index INTEGER NOT NULL,      -- 0, 1, 2, ... for team assignment
    drink_count INTEGER NOT NULL DEFAULT 0,
    is_host INTEGER NOT NULL DEFAULT 0,
    joined_at TEXT NOT NULL DEFAULT (datetime('now')),
    is_connected INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE rules (
    id TEXT PRIMARY KEY,              -- UUID
    game_id TEXT NOT NULL REFERENCES games(id) ON DELETE CASCADE,
    team_index INTEGER NOT NULL,      -- which team this rule belongs to
    trigger_text TEXT NOT NULL,       -- e.g. "Someone says 'I'll be back'"
    trigger_description TEXT,         -- longer explanation for the rule
    category TEXT,                    -- 'catchphrase' | 'action' | 'theme' | 'character'
    times_triggered INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE drink_log (
    id TEXT PRIMARY KEY,              -- UUID
    game_id TEXT NOT NULL REFERENCES games(id) ON DELETE CASCADE,
    player_id TEXT NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    rule_id TEXT REFERENCES rules(id) ON DELETE SET NULL,
    team_index INTEGER NOT NULL,
    amount REAL NOT NULL DEFAULT 1.0, -- 1.0 = standard sip, scaled by chaos_level
    logged_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_players_game ON players(game_id);
CREATE INDEX idx_rules_game ON rules(game_id);
CREATE INDEX idx_drink_log_game ON drink_log(game_id);
CREATE INDEX idx_drink_log_player ON drink_log(player_id);
```

### JSON Message Protocol (WebSocket)

```typescript
// Client → Server
type ClientMessage =
  | { type: "join_lobby"; game_id: string; player_name: string }
  | { type: "create_lobby"; player_name: string; team_count: number }
  | { type: "start_game" }
  | { type: "log_drink"; rule_id: string }
  | { type: "trigger_rule"; rule_id: string }
  | { type: "leave_lobby" }
  | { type: "ping" };

// Server → Client (broadcast to room)
type ServerMessage =
  | { type: "lobby_state"; payload: LobbyState }
  | { type: "player_joined"; payload: { player: Player } }
  | { type: "player_left"; payload: { player_id: string } }
  | { type: "game_started"; payload: { rules: RuleSet } }
  | { type: "rule_triggered"; payload: { rule: Rule; team_index: number } }
  | { type: "drink_logged"; payload: { player_id: string; team_index: number; new_count: number } }
  | { type: "game_ended"; payload: { stats: GameStats } }
  | { type: "error"; payload: { message: string } }
  | { type: "pong" };
```

## API Routes

### REST Endpoints

```
# Movie Search (no auth needed — public)
GET  /api/movies/search?q={query}&type=movie|tv
  → { results: [{ tmdb_id, title, year, poster_url, overview }] }

GET  /api/movies/{tmdb_id}?type=movie|tv
  → { tmdb_id, title, overview, poster_url, cast: [...], genres: [...] }

# Game Management
POST /api/games
  Body: { movie_tmdb_id, movie_type, team_count, chaos_level }
  → { game_id, room_code }

GET  /api/games/{game_id}
  → { game: Game, players: [...], rules: [...] }

POST /api/games/{game_id}/rules/generate
  → Triggers async LLM rule generation, returns immediately
  → { status: "generating" }

GET  /api/games/{game_id}/rules/status
  → { status: "generating" | "ready", rules: [...] | null }

# Post-game
GET  /api/games/{game_id}/stats
  → { total_drinks, per_team: [...], per_player: [...], top_rules: [...] }

# Player history (post-MVP archive tab)
GET  /api/players/{player_id}/history
  → [{ game_id, movie_title, drink_count, played_at }]
```

### WebSocket Endpoint

```
WS   /ws/{game_id}?player_name={name}
  → Upgrade to WebSocket
  → Server registers connection in ConnectionManager
  → Client receives lobby_state on connect
  → Bidirectional JSON messages per protocol above
```

## LLM Prompt Design (Rule Generation)

The system prompt sent to the LLM to generate contextual rules:

```
You are a drinking game rule generator. Given a movie or TV show, generate
drinking game rules based on recurring elements, character catchphrases,
and iconic moments.

Output a JSON object with this exact structure:
{
  "rules": [
    {
      "trigger": "Short, punchy trigger text (max 80 chars)",
      "description": "One sentence explaining the rule context",
      "category": "catchphrase | action | theme | character",
      "frequency": "common | occasional | rare"
    }
  ]
}

Generate exactly {team_count * rules_per_team} rules total, split equally
across {team_count} teams. Rules should be:
- Specific to this movie/show (not generic "someone drinks")
- Varied across categories
- A mix of frequencies (some common, some rare for variety)
- Fun and social — encourage calling each other out

The chaos level is {chaos_level} on a 0-1 scale:
- 0.0 = sipping: mild, polite triggers, low drink frequency
- 0.5 = standard: balanced mix
- 1.0 = pounding: aggressive triggers, frequent drinks, chaotic

Input context includes movie title, overview, main cast, and genres.
```

#### Task 9: WebSocket connection manager

**Objective:** Build the ConnectionManager that tracks WebSocket connections per game room and handles broadcast.

**Files:**
- Create: `backend/app/websocket/__init__.py`
- Create: `backend/app/websocket/manager.py`

**Step 1:** Write `manager.py`:
```python
class ConnectionManager:
    def __init__(self):
        self.connections: dict[str, dict[str, WebSocket]] = {}  # game_id -> {player_id: ws}
    
    async def connect(self, game_id: str, player_id: str, ws: WebSocket):
        await ws.accept()
        if game_id not in self.connections:
            self.connections[game_id] = {}
        self.connections[game_id][player_id] = ws
    
    def disconnect(self, game_id: str, player_id: str):
        self.connections.get(game_id, {}).pop(player_id, None)
        if game_id in self.connections and not self.connections[game_id]:
            del self.connections[game_id]
    
    async def broadcast(self, game_id: str, message: dict):
        for ws in self.connections.get(game_id, {}).values():
            try:
                await ws.send_json(message)
            except Exception:
                pass  # Dead connections cleaned up on next ping
    
    async def send_to_player(self, game_id: str, player_id: str, message: dict):
        ws = self.connections.get(game_id, {}).get(player_id)
        if ws:
            await ws.send_json(message)
```

## Risks, Tradeoffs, and Open Questions

### Risks
1. **LLM rule quality varies** — Gemini Flash may produce generic rules for obscure movies. Mitigation: include detailed movie context in prompt, allow manual rule editing (post-MVP).
2. **WebSocket scaling** — single Python process handles all connections. For MVP with ≤50 concurrent users this is fine. If it grows, add Redis pub/sub and multiple uvicorn workers.
3. **SQLite concurrent writes** — WAL mode helps but write contention under heavy load could be an issue. Unlikely for this use case (party game, not high-frequency writes).
4. **TMDB rate limits** — free tier has rate limits. Add caching layer (in-memory TTL cache) for movie details.

### Tradeoffs
- **No authentication** — players identified by name only, no accounts. Simpler UX, but no persistence across devices (solved by room codes).
- **State-based routing** over React Router — less URL shareability but simpler for this use case. Can add React Router later.
- **CSS-only charts** over a charting library — smaller bundle, less dependency, sufficient for simple bar charts.

### Open Questions
1. **Win condition:** Team with most drinks wins, or team with least drinks wins? (Most drinks = most engaged with the movie = winning. Recommend: most drinks wins.)
2. **Rule triggering:** Who triggers a rule — any player who spots it? Or automatic? (Recommend: manual — any player taps their team's rule when they spot it. More social, avoids false positives.)
3. **Public lobbies vs room codes only:** Room codes only for MVP — friends share the code in person or via messaging app.
